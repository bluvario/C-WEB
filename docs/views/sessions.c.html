Sessions

Sessions put state on the server and hand the client an opaque token. The client can point the token at a session but can never read or forge its contents — the right primitive when almost anything else would let a visitor tamper.

The store

Every page in a generated app receives the shared session store as user_data:

<?c
  Http_Session_Store *store = (Http_Session_Store *)user_data;
  Http_Session *sesh = http_session_from_cookie(store, req, "app_session");
?>

http_session_from_cookie reads the named cookie, resolves it to a live session, and returns NULL when the cookie is missing or stale. That is the "load who is talking" step — call it at the top of every page that cares.

Creating a session

Sessions are created lazily, when a visitor logs in or shows a preference. Create one and issue its cookie in the same breath:

<?c
  Http_Session_Store *store = (Http_Session_Store *)user_data;
  const char *token = http_session_create(store, -1);   // -1: store default TTL
  http_session_issue_cookie(res, "app_session", token, NULL);
?>

The store was initialized with a default TTL (an hour of inactivity in the generated server); pass explicit seconds or -1 for the default, or 0 for a session that never expires.

Reading and writing

<?c
  http_session_set(sesh, "username", "ada");
  const char *name = http_session_value(sesh, "username");
?>
<p>Logged in as <?h= sv_from_cstr(name != NULL ? name : "nobody") ?></p>

Every session handle is server-side storage; the cookie only names it. Destroy a session (a logout) with http_session_destroy(store, token).

Persistence

Run the server with --db app.db and the store mirrors every session to the file-backed database: creates and every set() are written immediately, missing sessions are loaded back on demand, and logouts remove their record. Logins survive a restart as long as the same db file is passed again.

Flash messages

A one-shot notice that survives a redirect: the POST stores it, the next GET renders it once. Flash values live under reserved flash: keys, so they can never collide with your data. Every call is a safe no-op when sesh is NULL, so an anonymous visitor can hit a page that renders flash without crashing.

<?c
  // in the POST handler, before redirecting:
  http_flash_set(sesh, "ok", "Note saved.");

  // in the GET handler, wherever the notice should appear:
  http_flash_render(res, sesh);   // emits <div class="flash">...</div>
?>

Read a single flash value with http_flash_get if you want to render it yourself.

CSRF protection

Forms that mutate state should carry a per-session token so a cross-site request can never forge a POST. The flow:

<form method="post">
  <?c http_csrf_field(res, sesh); ?>
  <button>Delete</button>
</form>
<?c
  if (http_csrf_verify(params, sesh) != 0) {
      http_csrf_reject(res, "/");   // 403 + a retry link
      return;
  }
?>

Rotate the token the moment a login succeeds (http_csrf_rotate(sesh)) so a token planted before authentication cannot be reused against the fresh session.

Do not skip this. A session cookie plus any body-changing form is exactly what CSRF attacks are built on. The token costs two lines. Best practice: rotate on login, verify on every mutating POST.

Basic auth (the simple version)

For a whole-app gate, HTTP Basic auth beats building a login page — the generated server's --basic-auth USER:PASS guards everything and fills req->auth_user for you. The comparison runs on constant-time SHA-256 digests, so a timing side channel cannot leak how much of a guess was right:

<?c if (req->auth_user.count != 0) { ?>
  <p>Hello <?h= req->auth_user ?></p>
<?c } ?>

Session-based login guards

For form-driven logins, two middlewares turn the session store into an authentication source: http_session_auth_middleware copies the stored auth_user (and a comma-separated auth_roles) into the request without blocking, and http_require_auth_middleware gates the chain behind them — 401 (or a 303 to a login path) for anonymous callers, 403 (or a 303 to a forbidden path) for logged-in callers who lack any required role. Store the password with cweb_password_hash at signup and check logins with cweb_password_verify (PBKDF2-HMAC-SHA256, no extra dependency):

<?c
  Http_SessionAuth_Options sa = { .store = &store, .cookie_name = "sesh" };
  http_middleware_add(&chain, http_session_auth_middleware, &sa);
  const char *roles[] = { "admin" };
  Http_RequireAuth_Options ra = { .roles = roles, .roles_count = 1 };
  http_middleware_add(&chain, http_require_auth_middleware, &ra);
?>

The setup is identical inside a page file or a hand-written main.c. Pages can then read req->auth_roles with the same ownership rules as req->auth_user.
