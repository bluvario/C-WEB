HTTPS / TLS

HTTPS is optional and additive. The framework builds and serves plaintext even when OpenSSL is absent; when the library is present (pkg-config finds it), the same generated server gains --tls, --tls-cert and --tls-key, and the module src/http/tls.c joins the build.

Requirement

OpenSSL headers and library, found through pkg-config. If you already built without it, just re-run make after installing it — the build picks it up automatically and test_tls joins the suite.

HTTPS in one flag

The easiest path: --tls. The first run mints a self-signed RSA certificate under ~/.cweb and reuses it on every later start, so the certificate's thumbprint stays stable across restarts:

./out/server --port 8443 --tls
# cweb: HTTPS on 0.0.0.0:8443 (self-signed, cert under ~/.cweb)

Connect with curl's trust-on-first-use mode against the literal key, or just accept the warning on a throwaway host:

curl -k https://localhost:8443/
Trust on first use. The server prints its certificate fingerprint; pin it the first time and reject changes afterwards. Self-signed is fine for internal services and testing. For a public endpoint, use your own cert (below).

Your own certificate

Two flags take a PEM chain and its private key:

./out/server --port 8443 \
  --tls-cert /etc/letsencrypt/live/example.com/fullchain.pem \
  --tls-key  /etc/letsencrypt/live/example.com/privkey.pem

When --tls-cert/--tls-key are set, the whole listener serves HTTPS and plaintext requests to that port are rejected — generated servers do not silently downgrade.

Behind a reverse proxy

Terminate TLS at nginx, Caddy, or whatever fronts the server, and let the proxy talk to C-WEB over a unix socket or localhost. See --socket PATH to expose the app on a local socket file, and --trusted-proxy so the real client address (X-Forwarded-For) is believed only when the request arrived from one of your proxy networks. That combination — TLS at the edge, plaintext on a socket, trusted proxy for IPs — is the recommended production shape.

HTTP/2 over TLS

With OpenSSL serving HTTPS, HTTP/2 is negotiated via ALPN transparently. Modern browsers speak h2 to the TLS port automatically; the h2c path is what cleartext clients use. See HTTP/2.

Inside the server

The transport is a thin layer over the same connection loop (tls.h): accept, wrap, read via tls_recv, write via tls_send_all. Handlers don't know or care whether the bytes traveled encrypted — templates, sessions, middleware and streaming behave identically.
