Middleware

Middleware runs around the request handler: it may inspect or modify the request, let the rest of the chain run, then inspect or modify the response on the way out. A chain is the framework's way of applying cross-cutting concerns — hardening, throttling, compression, logging — to every request without touching the handlers.

The chain

Through the library, a chain is assembled and then used as the top-level handler:

Http_Middleware_Chain chain;
http_middleware_init(&chain);
http_middleware_add(&chain, http_security_middleware, NULL);
http_middleware_add(&chain, http_rate_limit_middleware, &limiter);
http_middleware_add(&chain, http_gzip_middleware, NULL);

Http_Handler_Fn dispatch =
    http_middleware_build(&chain, router_dispatch, &r, &chain_data);
Http_Server_Config cfg = {0};
http_serve(listener, dispatch, chain_data);

Middlewares run in the order added. The returned handler is fn(req, res, handler_data); forfeit it with http_middleware_data_free when the server stops.

Built-in middleware

The generated server mounts these with a one-word flag, which is the easiest way to use them. The library forms are there when you hand-build.

MiddlewareFlagWhat it does
http_security_middleware--secureStamp nosniff, no-referrer, DENY and a Content-Security-Policy (default-src 'self' by default) on every response.
http_rate_limit_middleware--rate NToken-bucket: up to N requests a minute per caller, 429 when the bucket empties.
http_gzip_middleware--gzipCompress compressible bodies over a size threshold; the client decides with Accept-Encoding.
http_etag_middleware--etagSHA-256 the body into a strong ETag; a matching If-None-Match gets a 304 with no payload.
http_basic_auth_middleware--basic-auth U:PRequire HTTP Basic credentials; 401 + challenge otherwise. Works from a SHA-256 digest, compared in constant time.
http_signature_middleware--signature-secret SRequire an HMAC-SHA256 signature over the request; 403 otherwise. For trusting another proxy.
http_request_id_middleware--request-idStamp each response (and req->request_id) with a unique trace id.
http_client_ip_middleware--trusted-proxy CIDRResolve the real client from X-Forwarded-For, but only when the request arrived from a trusted proxy network — so logs and rate buckets name the client, not the proxy.
http_cors_middleware--cors ORIGINAnswer preflights and stamp Access-Control-Allow-Origin on matching requests.
http_access_log_middleware--log FILEOne Common Log Format line per completed request, naming the real client and echoing the request id when one exists.

Ordering matters

The generated server composes the chain in a deliberate order (outermost first): trusted-proxy resolution, request-id, security headers, request signature, rate budget, basic-auth guard, gzip, etag, CORS. The point of a few of those choices:

  • The rate budget sits outside basic auth, keyed by the account the request names — so brute-forcing one account is throttled however many IPs the attacker spreads across, instead of rerolling the bucket on every try.
  • client-ip runs outermost, so access logs and the per-address buckets below it see the real client, never the proxy.
  • request-id runs outermost, so even a short-circuited chain still carries the trace id.
  • gzip runs outside etag because the ETag hashes the uncompressed body for a stable validator across encodings.

When you override a policy role with flags like --csp or --cors, only that knob changes — the ordering stays.

When to skip the chain

A middleware chain is the right tool for cross-cutting behavior. For one-route concerns — a single admin endpoint, a handler that wants no layout — do it in the handler instead: http_basic_auth_middleware wraps one handler, http_response_security_headers stamps one response, res->no_layout skips the wrapper.
