The accounts app

cweb new --login scaffolds the whole account side of an app — signup, login, logout and a private dashboard — wired the way the framework recommends. This page walks it route by route: what each page does, which library pieces it leans on, and what you would change to fit your own app.

Scaffold and run

cweb new --login app
cd app
cweb serve views 8080 .. static --db app.db

The first command creates views/ (index, layout, 404, login, signup, logout, dashboard), static/style.css and a .gitignore. The second compiles and serves it. Note --db app.db: the whole app runs on the file-backed store — users, sessions and session-db is what survives a restart.

The route map

Signup: the write path

The POST branch does, in order: throttle-check, input checks, then

<?c
  char key[512];
  snprintf(key, sizeof key, "user:%s", username);
  if (cweb_db_get(db, sv_from_cstr(key)).count > 0) {
      error = "that username is taken";
  } else {
      char hash[CWEB_PASSWORD_HASH_MAX];
      cweb_password_hash(password, 0, hash, sizeof hash);
      cweb_db_put(db, sv_from_cstr(key), sv_from_cstr(hash));
      cweb_db_sync(db);
      char *token = http_session_create(sessions, 3600);
      Http_Session *sesh = http_session_open(sessions, token);
      http_session_set(sesh, "username", username);
      http_csrf_rotate(sesh);
      http_session_issue_cookie(res, "cweb_session", token, NULL);
      http_response_redirect(res, HTTP_303_SEE_OTHER, "/dashboard");
  }
?>

Three things worth stealing:

  • Users are db rows. An account is the single key user:<name> holding a PBKDF2-HMAC-SHA256 hash (see cweb_password_hash in password.h). No schema, no table; --db is just a string-keyed store.
  • Signup auto-logs-in. One session created, one username claim, the CSRF token rotated to the fresh session — a token minted before authentication can never be replayed against it.
  • Passwords never reach the page. Only the digest is stored, and cweb_password_verify runs in constant time on the login side.
Note: making the pre-auth CSRF token a null session is a deliberate pattern: http_session_from_cookie on an anonymous visitor returns NULL, so the auth forms carry no token until one exists.

Login: the check path

Nearly the reverse, plus two guards a signup does not need:

<?c
  if (cweb_login_throttle(req, res, params, "username") != 0) {
      return; // a 429 with Retry-After is already on the wire
  }
  ...
  if (cweb_password_verify(password, hash) == 1) {
      ... create session, rotate CSRF, Set-Cookie, 303 /dashboard ...
  }
  error = "username or password is wrong";
?>

The same error string for an unknown user and a bad password keeps an attacker from probing which usernames exist. And the throttle is checked before the expensive part: cweb_password_verify is PBKDF2 and takes the better part of a second; the bucket guard stops a guesser from ever reaching it once the budget is spent.

The brute-force guard

Every generated app — accounts or not — links a cweb_login_throttle helper, driven by the rate limiter the middleware docs use globally. The scaffold calls it with the policy that fits auth flows:

  • Login keys on the claimed username. Hammer one account and that account dries up (rate 1/s, burst 3) while every other user's form still works. The bucketed key is the username the client submitted, so an attacker who rotates names gets a fresh budget per name — exactly the trade-off a per-account guard makes.
  • Signup keys on the caller's address (username_key == NULL): account-creation floods are capped by source rather than by an endless supply of new names.
  • A dry bucket answers 429 with a Retry-After and a plain-text reason; the helper returns -1 so the page returns immediately. No PBKDF2 burn, no form re-render.

Try it with curl: six wrong logins in a row get you the first guesses answered normally, then a visible wall.

for i in 1 2 3 4 5 6 7 8; do \
  curl -s -o /dev/null -w "%{http_code} " \
    -d "username=alice&password=bad-$i" http://localhost:8080/login; done; echo
# 200 200 200 200 200 200 429 429

Logout and the private page

The logout form lives on the dashboard and posts through a CSRF token; the handler destroys the session server-side and clears the cookie with an empty value — the token is dead in both places. The dashboard is the template for every gated page: look the cookie up, bounce when it is missing, render only then.

What to change for your app

  • Session lifetime — http_session_create(sessions, 3600): replace 3600 (seconds) with your idle policy, or -1 for the store default.
  • Cookie name — cweb_session in http_session_from_cookie and http_session_issue_cookie; change it everywhere at once.
  • Password policy — the 8-character floor is in signup.c.html; the hash iteration count is the second argument of cweb_password_hash (0 picks the default).
  • Throttle budget — http_rate_limiter_init(&cweb_login_rl, 1.0, 3.0) in the generated main.c: tokens per second, then burst.
  • Key prefix — user: duplicates to other namespaces are fine, just keep one prefix per kind of row.
